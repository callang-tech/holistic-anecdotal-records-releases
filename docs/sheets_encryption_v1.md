# Google Sheets encryption v1

Local SQLite and all domain/sync comparisons remain plaintext. Production Sheets
record operations require a locally installed key, including empty-table reads.
There is no production legacy-plaintext switch. `forLegacyPlaintextTesting` is
only for existing synthetic regression fixtures.

## Wire format and field policy

`ENC:v1:<32-lowercase-hex-key-id>:<base64url(nonce || ciphertext || tag)>`

AES-256-GCM from cryptography 2.9.0, 12 random nonce bytes per value, 16-byte tag.
The encrypted UTF-8 JSON scalar preserves null, strings (including empty and
whitespace-only), and integer values. All protected cells, including nulls, have
an envelope. Reserved `ENC:` input must authenticate before it can pass through
without double encryption; literal user text beginning with that prefix is
rejected rather than guessed to be plaintext.

AAD is the UTF-8 JSON array `["holistic-fields-v1", keyId, datasetId, sheetTitle,
columnName, trimmedSyncID, trimmedLearnerSyncIDOrEmpty, integerDeleted]`.
The random dataset ID travels with the recovery package; it is independent of
Google spreadsheet ID, so a copy of the same encrypted dataset remains readable.
Local numeric IDs are not authenticated as stable identity. CreatedAt, UpdatedAt,
DeviceID and Version remain plaintext and are not authenticated by this v1 policy.
Deleted and child LearnerSyncID are authenticated. AEAD does not provide replay
protection; the existing semantic conflict rules and remote read/write race are
unchanged. Future format changes must use a different policy/envelope version.

Every nontechnical column is encrypted, including teacher Status:

| Sheet | Protected columns |
|---|---|
| LEARNERS | LearnerReferenceNumber, LastName, FirstName, MiddleName, Sex, BirthDate, Age, PersonalContactNumber, RegionCode, Region, ProvinceCode, Province, CityMunicipalityCode, TownMunicipality, BarangayCode, Barangay, Purok, Street, HouseNo, Parents, Guardian, RelationshipToGuardian, ParentsContactNumber, NotesDetails |
| TEACHERS | TeacherName, MobileNumber, Status |
| SECTIONS | SchoolYear, GradeLevel, SectionName, Adviser |
| SCHOOL_HISTORY | SchoolYear, Grade, School, Section, Adviser, NotesDetails |
| INCIDENTS | IncidentDate, IncidentTime, Observer, BehaviorProblem, ObservationDetails, Intervention, ActionTaken, Remarks, Details |

Headers, SyncID, local numeric IDs, child LearnerSyncID, CreatedAt, UpdatedAt,
DeviceID, Version and Deleted remain plaintext. This reveals record counts,
relationships and synchronization metadata, not the protected domain contents.

## Key management

Setup generates a 32-byte key, a random 16-byte key ID, and an independent random
16-byte dataset ID. WindowsDatasetKeyStore uses native user Credential Manager
CredRead/CredWrite through win32 6.4.0 and ffi 2.2.0. The credential target is
`HolisticAnecdotalRecords/DatasetKey/v1`; persistence is CRED_PERSIST_LOCAL_MACHINE
(the same user's subsequent logons on this device, not all machine users).
Only ERROR_NOT_FOUND means no key. Other failures are errors; no secret-file,
SQLite, SharedPreferences or machine-derived-key fallback exists. Native secret
buffers are zeroed before being released. Dart-managed copies cannot be promised
complete memory erasure.

flutter_secure_storage was evaluated and removed: the resolved Windows backend
used DPAPI files with corrupt-file deletion and an indefinite file-write retry.
Direct Credential Manager gives this small key record a simpler failure boundary.
No installer, native plugin registration, or CMake changes are required.

The `.harkey` recovery file is JSON containing public version, key ID, dataset ID,
KDF name, fixed iteration count, random salt, and encrypted payload. The payload
contains the key record; it is AES-256-GCM protected with a fresh 12-byte nonce,
16-byte tag, and a password-derived 256-bit key. KDF: PBKDF2-HMAC-SHA256, 600,000
iterations, random 16-byte salt. All public recovery metadata is authenticated as
AAD. Export requires at least 16 password characters and matching confirmation.
The password is never saved. KDF work executes in a separate isolate.

Import authenticates everything before writing; an existing key requires explicit
replacement confirmation. Transfer the protected recovery file and its password
separately, import on device two, and Windows protects that device's copy. Import
preserves the exact key, key ID and dataset ID. There is no cloud key distribution
or rotation in v1. Keep the recovery file and password safe; neither a Google
login nor an app password reset can recover a lost dataset key.

Key mutation shares the existing SyncContextService operation guard with sync,
restore and target switching, so an in-flight operation cannot change keys midway.
No key is automatically generated by a read, download, sync or restore.

## Integration and safe deployment

SheetsEncryptionCodec runs in GoogleSheetsService.upsertRowsBySyncId before the
raw writer. All outgoing values are prepared before any row is written.
downloadTable, downloadSheetRows (including findRemoteRecordBySyncId), and the
final upsert reread decrypt before returning/comparing maps. The generic raw
range/header methods remain transport-only. SyncService needs only a reconnect
preflight: authentication of all tables precedes ownership/baseline changes.
Restore already downloads all five tables before its SQLite transaction.

Missing key, wrong key, unknown key ID, malformed/unsupported envelope, bad tag,
cleared protected cell, plaintext protected field, and secure-store failure all
stop synchronization. Crypto errors never substitute empty text or ciphertext.
No baselines advance on required download decryption failure. A failed restore
does not replace records or ownership. An authenticated envelope larger than a
Sheets cell is rejected before upload.

Set up encryption (or import the existing dataset's recovery file), export a
recovery copy, and explicitly choose/create a fresh Sheet through the existing
Admin workflow. Existing plaintext Sheets are rejected. There is no automatic
migration or rewrite of old Sheets. Old app versions must not share the new
encrypted Sheet. Existing plaintext exports/copies remain plaintext.

## Validation boundaries

Automated tests use synthetic values, memory key stores, mock network transport
and temporary SQLite. The actual Windows credential vault and real Sheets are
not touched by tests. Interactive checks still needed before release: Credential
Manager setup/persistence and error behavior under a disposable Windows account;
file-picker recovery export/import/cancel/confirmation on two authorized devices;
and a fresh disposable Sheet end-to-end smoke test (never production data).
No release build, app launch, installer or updater is part of this implementation.
